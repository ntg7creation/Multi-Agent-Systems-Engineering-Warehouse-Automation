# Architecture Decision

## Selected Architecture

The Vercel build uses Pyodide in a dedicated Web Worker.

React renders the application shell, the copied 2D dashboard, and the copied Three.js viewer. A singleton `PyodideSimulationAdapter` owns one browser worker for the tab. The worker loads Pyodide, copies the Python simulation files into Pyodide's virtual filesystem, imports `pyodide_bridge.py`, and executes request-driven simulation commands.

Routes:

- `/` and `/2d`: copied 2D React simulator.
- `/3d`: copied Three.js simulator.

Both routes use the same adapter instance in a tab, so switching between `/2d` and `/3d` keeps the active simulation session.

## Why Pyodide Was Selected

The existing backend API is Flask, but the simulation engine itself is pure Python. The core files under `backend/models`, `backend/scenarios.py`, and `backend/strategy_config.py` use standard-library modules such as `dataclasses`, `random`, `heapq`, `uuid`, `csv`, `io`, `pathlib`, and JSON file reads. They do not require sockets, subprocesses, multiprocessing, native extensions, a database, or a long-lived OS service.

The server-only pieces are:

- `backend/app.py`: Flask routes.
- `backend/services/simulation_service.py`: process-global service, lock, and autorun thread.

Those pieces were not copied as runtime dependencies. Their route behavior was adapted into:

- `src/simulation/PyodideSimulationAdapter.js`
- `src/simulation/simulationWorker.js`
- `public/python/warehouse_simulation/pyodide_bridge.py`

This preserves the Python engine as the source of behavior without requiring a hosted Python server.

## Rejected Options

### Vercel Python Functions

Vercel Python Functions were less appropriate because the original backend assumes a persistent process-global `SimulationService`. A correct serverless version would need to serialize and send the full simulation state on every request or introduce persistence. The user explicitly selected Pyodide unless blocked, and no Pyodide blocker was found.

### Dedicated Flask/FastAPI Server

Rejected because the deployment must not require a separate Python server, Docker container, VM, or dedicated backend service.

### Complete JavaScript Rewrite

Rejected because the Python engine is compatible with Pyodide and remains the authoritative implementation. JavaScript only handles worker messaging, playback timing, downloads, routing, and UI integration.

### Hybrid

Rejected because no essential feature required a Vercel Function. Analytics export is generated by Python and downloaded from the browser using `Blob`.

## Dependency Check

Runtime dependencies actually imported by the copied simulation:

- Python standard library: compatible with Pyodide.
- `pathlib`: compatible; used against Pyodide's virtual filesystem.
- `csv` and `io.StringIO`: compatible; used for CSV string export.
- `uuid`, `random`, `heapq`, `collections`, `dataclasses`, `typing`: compatible.

Dependencies listed in the original `backend/requirements.txt` but not imported by the copied engine:

- Flask and flask-cors: server layer only; intentionally not loaded.
- networkx, numpy, pandas, pydantic: not used by the current copied simulation path.
- pytest: test-only.

## Compatibility Issues And Adaptations

- Flask routes were replaced with adapter commands.
- The original autorun thread was replaced with a browser-side interval in `PyodideSimulationAdapter`; each interval enqueues one `STEP` command and prevents overlapping steps.
- Scenario files are copied to `public/python/warehouse_simulation/scenario_data` and then loaded into Pyodide's virtual filesystem through `python-manifest.json`.
- Analytics downloads no longer use server attachment responses. The browser creates JSON or CSV downloads with `Blob`.
- The app does not persist large replay data to `localStorage`; active data lives in worker memory.

## State Preservation And Isolation

The current simulation engine lives in `pyodide_bridge.py` as `_engine`, but that module is loaded inside a dedicated browser worker. Each browser tab gets its own worker and Pyodide runtime, so users and tabs are naturally isolated from each other.

Within one tab, route switching keeps the same singleton adapter and worker. A page refresh creates a new worker and restarts the simulation from the default scenario unless the user loads another scenario.

## Frontend Communication

The old frontend calls such as `fetch("/api/tick")` were replaced by adapter methods:

- `getState()`
- `listScenarios()`
- `reset()`
- `step()`
- `run()`
- `start()`
- `pause()`
- `getAnalyticsSummary()`
- `exportAnalytics()`

The adapter sends typed messages to the worker. The worker calls `pyodide_bridge.handle(...)`, receives JSON-compatible data, and returns structured success/error responses.

## Vercel Limitations Considered

- No reliance on process globals across requests.
- No server filesystem writes.
- No long-running backend process.
- Static assets are served from the Vercel project root.
- `/2d` and `/3d` are rewritten to `index.html` for direct navigation.
- The Pyodide runtime is copied into `public/pyodide` during `npm run build`.

## Behavior Differences

- Start/resume playback is now a JavaScript timer, not a Python background thread.
- Refresh restarts the in-memory browser worker session.
- Downloads are browser-generated instead of server-generated attachments.
- Initial load takes longer because Pyodide and the Python standard library must load in the browser.
